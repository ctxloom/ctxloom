# P0 4e — relocate the launch backends into the agent packages

Status: analyzed, not started · 2026-06-05 · session `tiny-loud-lark`
Parent: `./p0-execution.plan.md` (phase P0, step 4e)

Goal: make `internal/agent/claude` and `internal/agent/gemini` the *full* agents —
launch (`Backend`) as well as settings (`SettingsWriter`, done in 4c/4d). Move
`claudecode.go` + `claude_capabilities.go` → `internal/agent/claude`, and
`gemini.go` + `gemini_capabilities.go` → `internal/agent/gemini`.

Unlike 4a–4d this is **not a lift-and-shift** — there is a real import cycle to
break first. It needs a design decision before any code moves.

## Dependency picture

```
launch backends (embed BaseBackend):  claudecode.go  gemini.go  codex.go  mock.go
                                              \___________\________/________/
                                                          v
                                            base*.go  (BaseBackend + capability bases)
                                                          |  outward calls:
                    WriteSettings(name, …) ───────────────┤   base_lifecycle.go:79/87, base_mcp.go:77
                    AssembleManagedHooks(…) ──────────────┤   base_lifecycle.go:103
                    WriteContextFile(workDir, frags) ─────┘   base_context.go:21
```

- `BaseBackend` (`base.go` + `base_lifecycle.go` + `base_mcp.go` + `base_context.go`, ~451 LOC) is embedded by **all four** backends — including `codex` and `mock`, which have no agent package.
- `WriteSettings(name, …)` is the **settings-writer registry dispatch** (hooks.go) — it imports `internal/agent/claude` + `internal/agent/gemini`.

## The blocking cycle (the thing to solve)

If `BaseBackend` moves to `agent`, its call to `WriteSettings` makes:
`agent → backends(registry) → agent/claude → agent` … a cycle.
So **`BaseBackend` must not call the registry dispatch directly.** The other two
hub calls are fine to relocate:
- `AssembleManagedHooks` + the context-injection web → no reference to the agent packages, can move to `agent`.
- `WriteContextFile` (contextfile.go) → no agent-package reference, can move to `agent`.

**Decision required — how to break the `WriteSettings` edge:**
- **B (recommended): inject it.** Give `BaseBackend` a `writeSettings func(...)` field, set by whoever constructs the backend (the registry/wiring in `backends`, or ctxloom's `cmd` wiring). `BaseBackend` + the launch backends then move to `agent` with no dispatch import. Smallest code move; one contract change (BaseBackend constructor). The context-injection web + `WriteContextFile` can be injected too, or moved to `agent` (they’re cycle-free either way).
- **A: move the web.** Relocate the context-injection subsystem + contextfile into `agent`, but `WriteSettings` *still* can’t move (it imports the agent packages), so A alone does **not** break the cycle — you end up doing B for `WriteSettings` regardless. A is strictly more work than B.

- **DI surface** — inject only `WriteSettings` (minimum to break the cycle), or also `AssembleManagedHooks`/`WriteContextFile` for a clean BaseBackend? Recommend: inject `WriteSettings` only; move the other two into `agent` (they’re cycle-free), so BaseBackend calls them directly.
- **codex/mock** — they embed `BaseBackend`; once it’s in `agent` they import `agent` (fine). They are NOT getting their own package in this plan.
- **Test moves** — `claudecode`/`gemini` + capabilities each have substantial tests; expect a 4c-style split, plus the base/context/rendezvous tests move with their code.
- **Biggest single phase** — 4e-ii (moving the shared launch substrate) is the heavy one; do it as its own green commit before any per-agent move.
- **Not on the critical path** — the settings extraction (4c/4d) already killed the churn and unblocked ltk. 4e is launch-side completeness; it can wait without blocking step 5 (ltk cross-tool).
