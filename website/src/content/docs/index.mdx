:::note[Why not just CLAUDE.md?]
Claude Code has `CLAUDE.md` - but it is **project-level only** and encourage intermingling project-specific context with general best practices. ctxloom separates concerns: your standards in a personal remote, project context in `.ctxloom/`, team standards in shared remotes. Fragments and commands can also be distilled by a cheap, fast LLM, so a long guideline costs fewer tokens every session.

**ctxloom does not stop Claude Code from reading `CLAUDE.md`.** `ctxloom run` hands its assembled context to Claude Code on a separate channel, and Claude Code still loads any `CLAUDE.md` in the project tree as it always does, so a standard kept in both places is delivered twice. Keep your standards in fragments, not in `CLAUDE.md`. For a Claude Code you launch yourself, `ctxloom profile materialize` appends the assembled context to the target's `CLAUDE.md` and leaves the hand-written part in place.
:::

## What ctxloom Does

| Capability | Description |
|------------|-------------|
| **Context Assembly** | Combine fragments into profiles, deliver to Claude Code through the engine's own context channel |
| **Slash Commands** | Commands become `/commands` in Claude Code automatically |
| **Session Memory** | Recover context after `/clear`, or pick up an earlier session |
| **Remote Pull** | Pull bundles from GitHub/GitLab, lockfile for reproducibility |
| **Token Optimization** | Distill fragments and commands with a cheap, fast LLM |

## Quick Example

```bash
# Initialize
ctxloom init

# Review what the remotes shipped - pulled content is withheld until you accept it
ctxloom review

# Run with context fragments (-f takes FRAGMENT names, not bundle names)
ctxloom run -f go-rules -f tdd "implement auth"

# Pull in a whole bundle's worth of context by tag
ctxloom run -t security "implement auth"

# Use a profile (pre-configured bundle/fragment set)
ctxloom run -p backend-developer "review this PR"

# Reference a remote bundle in a local profile, then pull
ctxloom profile create testing -b ctxloom-default/testing
ctxloom deps pull
```

## Slash Commands

Commands in bundles become slash commands in Claude Code:

```yaml
# .ctxloom/content/bundles/v2/my-tools.yaml
commands:
  code-review:
    description: "Review code for issues"
    content: |
      Review this code for:
      - Security vulnerabilities
      - Performance issues
      - Best practice violations
```

Then in your AI CLI:
```
/code-review src/auth.go
```

## Session Memory

Claude Code's `/compact` has a fundamental flaw: it needs context space to run, but you only think to use it when context is almost full. You try `/compact`, it fails, and you're stuck.

**ctxloom works after exhaustion:**

1. **Clear** - Run `/clear` when you hit context limits
2. **Recover** - Ask the agent to resume; it calls ctxloom's `recover_session` MCP tool, which distills this session's transcript from disk
3. **Continue** - The summary is loaded back in, you keep working

ctxloom reads the raw JSONL transcript from disk and uses a separate LLM (the `fast` default, Haiku as `ctxloom init` scaffolds it) to distill it, outside your exhausted context window.

`/clear` keeps the same session alive, so `recover_session` is the post-`/clear` path. To pull in an **earlier** session instead, the agent uses `get_previous_session` or `load_session`, or you start a new run from one with `ctxloom run --session <harp>`.

## How It Works

```mermaid
flowchart LR
    Bundles["Bundles<br/>(fragments)"] --> Profiles["Profiles<br/>(combos)"]
    Profiles --> Context["Context<br/>(assembled)"]
    Bundles --> Remotes["Remotes<br/>(GitHub/GL)"]
    Context --> AI["Claude Code<br/>(native context channel)"]
```

1. **Bundles** contain fragments (context), commands (slash commands), and MCP servers
2. **Profiles** combine bundles with inheritance and exclusions
3. **Context** is assembled and handed to the engine on its own context channel - Claude Code is launched with `--append-system-prompt-file`. The same session also carries ctxloom's MCP server, served by the running session, which your agent can *retrieve* from mid-session. Nothing is registered in the project itself.
4. **Remotes** provide team sharing and community bundles. Pulled content is withheld from the agent until you accept it with `ctxloom review`

## Core Concepts

| Concept | What It Is |
|---------|------------|
| **Fragment** | A piece of context (guidelines, patterns, examples) |
| **Command** | A saved prompt template, exported as a slash command |
| **Bundle** | A versioned YAML containing fragments + commands + MCP servers |
| **Profile** | A named configuration referencing bundles/tags |
| **Remote** | A GitHub/GitLab repository containing bundles |

## Running

```bash
# Launch Claude Code with assembled context, ctxloom's hooks and its MCP server
ctxloom run -p developer "help with code"

# Write a profile into a directory for a Claude Code you launch yourself
ctxloom profile materialize developer --target .
```

ctxloom's own MCP server exists only inside a `ctxloom run` session. A materialized profile carries the context, hooks, commands and the MCP servers its bundles declare, but not ctxloom's; a Claude Code launched with neither gets nothing from ctxloom.

## Configuration

```yaml
# .ctxloom/config.yaml
llm:
  defaults:
    primary: claude-code

# The always-bound default agent. Its composed profiles are the context
# you get when you run with no -p/-f/-t.
default_agent: go-developer
agents:
  go-developer:
    llm: claude-code
    profiles:
      - go-developer
```
