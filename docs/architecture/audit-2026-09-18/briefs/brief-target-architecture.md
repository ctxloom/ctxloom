## The human's constraints, verbatim — these are RULINGS, design inside them
- "we want to keep the engines in a plugin style architecture and delegate/pull engine specific data from each engine. each engine should be a package and polymorphic."
- "we want to assemble bundles and composite them from the repos, project, and companions and present that package for delivery via polymorphic mechanisms, both static (file based) and dynamic (mcp)."
- "DRY and reduce duplication."
- "we want hexagonal architecture, generally speaking" — ports and adapters: a core (the composite package, the resolved launch, identity, the bus verbs, sessions-on-disk policy) that depends on NOTHING outside itself and exposes PORTS as interfaces; every engine package, every delivery mechanism (static files, dynamic MCP), the CLI, the MCP server, the gRPC runner link, the filesystem, git remotes and companions are ADAPTERS on those ports. Dependency direction points inward only. Part 1.1's package map must show the hexagon: core in the middle, ports on its edge, adapters outside; tests/arch layering rules become the enforcement.
- "we know we want to remove the mcp callback and use a socket" / "that will keep the harp owner single" — the engine-spawned `ctxloom mcp serve` stdio shim (the MCP "callback" into ctxloom) is deleted; an engine addresses the runner's socket directly (deceased-yoga: authenticated loopback TCP, Streamable HTTP; unrefined-eternity; blissful-blah). Consequence the design must make structural: exactly ONE owner process per harp — no second process can become the owner (tacky-padding), no forwarding/discovery-marker tier, no hosted-coordinator constructor reachable from a shim (seam 2 F2/F3/F5). Session identity then has one minting process and the MCP server is an adapter INSIDE the runner, not a callback.
- "we know that we want to use/exploit session home to keep ctxloom sessions out of the project root, unless the agents select unsafe" — i.e. the SESSION HOME (the per-harp private engine home under ctxloom's own tree) is the default root for everything a session writes; nothing of a session lands under the project root unless the agent's binding explicitly selects the unsafe-file approach. This settles boned-monoxide item 1's direction and seam 3 F4's substitution sites: there is no "fall back to the shared home" arm.
- "we know we want a materialize that *does* write to the project root" — the explicit, human-invoked `materialize` (profile materialize / manage hooks install) is the ONE sanctioned writer into the project root: at-rest delivery for a human's own checkout, distinct from a session's delivery. The design must keep both and make them share the same package value and the same static-delivery writers, differing only in ROOT (project root vs session home) and OWNERSHIP RECORD, never in a second pipeline (seam 3 F16, install vs uninstall on different abstractions).
Standing rulings you must not contradict without flagging them (each is a task row or a recorded decision; cite it if you diverge): engines are integrated through their NATIVE surfaces, never private internals (fail loud where none exists); delivery never degrades and is never shared by default — the private engine home is the root, the shared host home only when explicitly selected; isolation has two independent axes (runtime: host|container-rootless|container-rootful; workspace: none|worktree), an ownership mismatch is fatal, never a substitution; every run mints a harp (scant-undoing); bytes are verified before delivery, the preimage is computed in one place per item kind (seam 5 confirmed), content_hash is an index never an authority; the `earthly-city` ruling ("one launch path, complete surface pipeline, hooks ON") was closed as superseded by code that moved the other way — the synthesis flags it for re-rule; the runner hosts MCP over authenticated TCP and the stdio shim is deleted (deceased-yoga ruling); intra-bundle links are a tag on each item (valid-vanish); session state leaves the project (boned-monoxide item 1, gated on night/obedient-railing).
